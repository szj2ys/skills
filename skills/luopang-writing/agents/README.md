# subagent 派发规范

**为什么要有这一层**：`scripts/` 只会数数，判断不了质量。实测一段通篇抽象、无真反转、无金句的空话稿，脚本给 95/100、FAIL 0——因为那 8 项"语义检查"只是关键词在不在。

凡是要**读懂**才能回答的问题，一律派 subagent。凡是要**数清楚**的，一律留给脚本（脚本数得比模型准，还便宜）。

---

## 四个角色

| 角色 | 文件 | 阶段 | 一句话职责 |
|---|---|---|---|
| **critic** 审读员 | `agents/critic.md` | S5 | 按 13 项评分表打分，每项给理由 + 引用原文 |
| **quote-miner** 金句矿工 | `agents/quote-miner.md` | S2 | 甄别检索器召回的候选，只留真金句 |
| **fact-checker** 事实核查 | `agents/fact-checker.md` | S1 / S5 | 核数字、引语、书名是否属实 |
| **reader** 读者替身 | `agents/reader.md` | S3 / S5 | 以"他"的身份读，做心坎测试与闭卷测试 |

---

## 什么时候派谁

| 体裁 | 派发组合 | 说明 |
|---|---|---|
| 短稿（60 秒） | **critic** | 一人够用，最省 |
| 长稿 | **critic ∥ fact-checker**（并行） | 长稿事实密度高，两件事互相独立 |
| 舞台体 | **critic + reader** | 舞台体最吃对象感；不跑脚本 |
| 金句阶段 S2 | **quote-miner** | 只在外部借句时派；用户素材够就不派 |

**可以并行的一定并行**（critic 与 fact-checker 互不依赖）；**不能并行的不要硬凑**（reader 必须在 S3 大纲后单独派，因为要防止主模型泄露意图）。

---

## 派发硬规矩

1. **给绝对路径**。subagent 看不到你的对话，草稿、读者卡、素材卡全部给绝对路径。
2. **给验收标准**。每份合同末尾都写了"验收"，派发时原样带上，不要自己改写。
3. **限制写权限**。subagent 只准写 `<scratch>/` 下指定的那一个文件，**一律不准改草稿本身**。改稿是主模型的活。
4. **不替用户编事实**。subagent 发现缺锚、缺机制、出处存疑时，只能**报告**，不准自己补。
5. **失败要看得见**。subagent 空返回 / 超时 / 明显跑偏时，主模型自己顶上，并在审核记录里写一行 **"降级为自审"**——**绝不静默跳过**。
6. **反谄媚**。评审类角色（critic / reader）的合同里都写了：第一条必须是指出的问题，禁止"整体不错，只是…"式开场。主模型复核时若发现通篇好评无一条实质批评，视为失败，重派。

## 与脚本的分工边界（别越界）

| 该谁干 | 例子 |
|---|---|
| **脚本** | 字数、禁用语、人称/问号计数、四拍编号、段落长度中位数、ripgrep 召回 |
| **subagent** | 锚是否真具象、反转是否到结构、是不是造词、金句成立与否、事实真伪、对象感 |
| **主模型** | 写稿、S3 闸门给用户的三个选项、最终采纳哪些修改 |

脚本产出的 **INFO 信号就是喂给 subagent 的线索**——信号说"检出年份 2019"，subagent 要回答的是"这个 2019 是不是真锚"。
