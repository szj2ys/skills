# Site Niche Loop — 选需求小闭环

把"做一个能赚钱的站"缩小成一次可验证的闭环：**选词 → 意图匹配 → 页面承接 → 观察反馈 → go/kill → 资产沉淀**。闭环越小，反馈越快，判断越准。

## 核心理念

- **先完成一次小验证，再谈赚钱。** 找一个已有人搜索、竞争不强的词，做出能用的页面，看有没有人从搜索结果进来。
- **反馈周期短是选小需求的全部意义。** 几天到几周内能看到收录和使用反馈；页面做得再完整，用户不搜这个词，代码写得越多越难停下来。
- **找词是固定入口的重复回访，不是临时想关键词。** 来源必须存档。
- **项目可以死，资产不能清零。** 每个站结束必须留下来源、页面参考、渠道记录。

---

## Phase 1: 两道验证门（选题前必过）

任何候选项目先问两个问题，**两个都没有答案就先不做**：

1. 这个需求能不能较快看到搜索反馈？（几天~几周内容易收录、有真实搜索）
2. 我能不能用现有能力把可用页面做出来？

典型失败模式：第一个项目选太难的需求，代码写完、页面上线，搜索里没位置、后台没用户，每天只剩改页面和怀疑方向。遇到这种情况，停掉项目，但模板代码留下复用。

## Phase 2: 找词（固定入口 + 趋势验证）

**禁止临时想关键词。** 先建立并存档固定找词入口清单（模板见 [references/asset-templates.md](references/asset-templates.md) 的「找词来源清单」），定期回访即可。

按赛道选入口：

- **游戏赛道**：已有大量用户的浏览器游戏网站（看最近上了什么新游戏、哪些在变热）、持续更新新游戏的网站、抢先试玩的 YouTube 创作者、活跃玩家社区。
- **AI 工具赛道**：新模型发布、工具目录站、YouTube 教程/测评、论坛里的实际用法讨论。
  - **模型名只是信号，不是需求。** 必须继续追：用户拿它做什么——修图、做角色、处理音频、生成哪类素材？这个具体动作才是页面要做的功能。

候选词用两个工具验证：

- 趋势工具（如 Google Trends）：判断词是不是"刚开始有搜索"。
- Google 搜索结果页：判断竞争强度——结果页里还没有多少专门页面 = 机会。

**反例**：看见一个词有热度，直接照着竞品首页做相似页面——很可能接错需求，必须先进入 Phase 3 判断意图。

## Phase 3: SERP 意图四分法（决定页面结构）

对每个候选词，先看搜索结果页判断用户意图，再决定页面类型：

| 意图 | 用户要什么 | 页面结构 |
|---|---|---|
| 直接玩 / 直接用 | 马上开始 | 入口放第一屏，越快给出越好 |
| 攻略 / 教程 | 玩法说明、步骤 | 结构化内容，工具入口反而是次要的 |
| 下载 | 安装包 / 链接 | 下载说明、平台兼容信息 |
| 找替代品 | 对比、迁移 | 对比表 + 替代方案 |

**同一个主题，不同意图的页面结构可能完全不同。** 围绕一个游戏/工具可以做多个意图不同的页面，但不要用一个页面硬接所有意图。

## Phase 4: 页面验收标准（上线前自检）

1. **价值前置**：想处理图片，进站就能上传并看到结果；想玩游戏，第一屏就是游戏入口。
2. **不拦注册**：用户还没体验到价值，邮箱/密码/验证码只会增加一次离开机会。**注册数 ≠ 需求成立**——先让用户完成一次操作，才能看他是否愿意继续用。
3. **生成类工具优化等待**：本身有等待时间，必须有进度反馈或示例结果；用户等很久看不到结果会直接走。
4. **复用模板**：基础页面和功能用上一个项目留下的架子，时间全部花在需求和页面上。

## Phase 5: 验证契约（go/kill）

上线前就定好观察项和止损条件，避免沉没成本：

- **观察三项**（窗口：几天~几周）：
  1. 词有没有人搜（趋势 + 实际曝光）
  2. Google 会不会收录（site: 查询 / Search Console）
  3. 用户进来后有没有使用（行为统计）
- **go**：有收录、有使用 → 进入推广（外链渠道单独建档，记录 schema 见 [references/asset-templates.md](references/asset-templates.md) 的「外链渠道台账」）。
- **kill**：窗口期内三项均无信号 → 停掉项目。**不要因为已经写了大量代码而继续耗。** 模板代码、找词来源、渠道记录全部转入 Phase 6。

## Phase 6: 复盘沉淀（每个站结束必做，无论成败）

强制留下三样资产，写入 [references/asset-templates.md](references/asset-templates.md) 的对应模板：

1. **找词来源**：本次发现的入口加入回访清单。
2. **页面参考**：哪种结构接住了哪种意图。
3. **渠道记录**：外链渠道的上线耗时、类型、是否带来访问/注册/订阅；同一渠道在不同站的结果都留档。

沉淀后回灌：来源清单喂给下一次 Phase 2，渠道记录喂给下一个站的推广。做过的项目越多，三个判断越具体：**这个词值不值得做、这个页面够不够用、这个渠道有没有效果。**

## 输出模板

```markdown
### 🎯 选词验证: [候选词]

#### 1. 两道验证门
- 搜索反馈周期: [预期几天/几周] ✅/❌
- 现有能力可交付: [能做出什么页面] ✅/❌

#### 2. 需求证据
- 找词来源: [哪个固定入口发现的]
- 趋势状态: [刚起势 / 平稳 / 衰退]
- 竞争强度: [SERP 里专门页面数量与质量]

#### 3. 意图判断
- 意图类型: [直接玩 / 攻略 / 下载 / 替代品]
- 页面结构: [对应结构一句话]

#### 4. 验证契约
- 观察窗口: [X 周]
- go 条件: [有收录 + 有使用]
- kill 条件: [窗口内三项无信号即停]

#### 5. 结论
- [做 / 不做 / 先补数据]
```

## 自检清单（发出前必须过）

1. 两道验证门是否都过了？没过就明确说"先不做"，不要勉强给方案。
2. 找词来源是否来自**已存档的固定入口**？新来源是否已建议加入清单？
3. 意图是否看过 SERP 才下结论，而不是照着竞品首页猜的？
4. 页面验收标准里"不拦注册"是否被遵守？
5. kill 条件是否写死？有没有防止"代码写多了舍不得停"的表述？
6. 结束时是否产出了三样资产？项目死了也不能跳过 Phase 6。
